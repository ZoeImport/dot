# 跨主机的网卡与服务验证

配置模板不包含 `interface-name`。不要将某台 Mac 的 `en0`、某台 Linux 的 `eth0` 或一次 Wi-Fi 测得的速率当成部署常量。主机的网卡存在、代理进程能启动、请求真正走指定出口，是三个不同结论。

## 逐台建立验证记录

对每台实际获授权的主机分别记录：系统和角色、内核/服务版本、当前网络、默认路由接口、候选绑定接口及其地址、客户端实际选中节点、HTTP/DNS/UDP 出口、配置校验和运行结果。记录放私有工作目录，仓库只保存通用方法。没有访问权限或没有实际测试的主机标记“未验证”，不能以其他机器的结果代替。

### macOS 客户端

1. 用 `networksetup -listallhardwareports` 识别物理网卡；用 `ifconfig INTERFACE` 核对接口状态和地址。不要根据 `en0` 名字推定它一定是 Wi-Fi。
2. 用 `route -n get VPS_IP` 检查到服务器的当前路由。TUN 启用时可能显示 `utun`，这说明当前路由情况，不足以证明出现回环或应强绑某个接口。
3. 从实际运行 core 的控制接口读取选中组、节点接口字段和 TUN 状态，确认修改的文件确实对应生效实例。
4. 先测无固定网卡的配置。若实测表明绑定物理网卡能改善当前 TUN 路径，仅在这台机器的专属配置/覆盖层设置，并对比真实客户端的同一小文件下载。再次验证 HTTP 出口与原生 UDP/STUN 出口。
5. 若机器需要切换 Wi-Fi、网线或热点，切换后重新做出口和连通性检查。绑定接口消失时应移除或调整该主机覆盖，不能让静态绑定进入跨平台共享模板。

### Linux 客户端或 VPS 服务端

1. 用 `ip -brief address` 识别地址与状态；用 `ip route get PEER_IP` 检查特定对端的路由和源地址。没有 `ip` 时先发现可用系统工具，不按历史接口名继续配置。
2. 区分公网地址直接配置在接口上，还是由供应商 NAT 提供。服务端 `bindIPv4` 必须是当前系统实际可绑定的本地地址；公网出口地址不在接口上时，不能直接把它写成本地绑定地址。
3. 对 systemd 服务读取 `systemctl show SERVICE -p User -p ExecStart -p FragmentPath`，核对真实服务用户、二进制和配置路径。分别查看 `systemctl is-active SERVICE`、`systemctl is-enabled SERVICE` 及 `ss -lntup`；监听端口不等于公网可达。
4. 在 VPS 上访问同一测试目标，建立服务端出站基线；从获授权客户端通过实际代理再测 HTTP 和 UDP/STUN 出口。只有客户端到服务的握手和数据都成功，才能确认公网入站链路可用。
5. 服务仅改过热加载配置时，不声称已验证开机自启。用户授权重启服务后检查启动结果；未做主机重启则明确未做完整重启验证。不能为了验证自动重启主机。

### iOS ClashMi

没有可用 shell 时，从 ClashMi 的运行状态、日志及连接详情确认内核已加载配置、VPN 已启用且选中正确节点。移除固定网卡和桌面隧道参数，由 iOS 网络扩展管理当前接口。分别在用户需要的 Wi-Fi/蜂窝网络上测试出口、DNS、WebRTC/UDP；仅有 Mac 的校验结果时，状态仍是“已适配，手机未实测”。

### 其他系统

先确认客户端和内核支持 Hysteria2，使用系统原生工具识别接口、路由和源地址。共享 YAML 默认自动选接口；不要复制 macOS/Linux 的接口名。无法在该系统验证时交付模板及明确的未验证范围，不保证与已测试主机同速。

## 数据面检查方法

- HTTP：通过目标客户端的实际本地代理访问可信出口回显服务，核对返回地址；浏览器启用 VPN 后也需在其真实路径检查。命令行测试时显式控制 `NO_PROXY` 和代理参数，避免环境变量导致绕过代理。
- UDP：向独立 STUN 端点发送请求，确认响应事务 ID，并解析映射地址。确认测试流量不会被既有直连规则放行；不要把 TCP 代理请求当成 UDP 证据。
- DNS：新随机域名或权威日志验证实际解析链路，区分用户保留的国内 DNS 分流；缓存命中不能证明新解析请求的路径。
- 性能：相同小文件、相同出口、相近时间比较自动接口与候选绑定。记录成功下载字节、完成耗时和超时，不能只选最小延迟节点就宣布“最快”。

接口检查和服务检查均通过后才更新该主机的验证状态。变更证书、网卡、运营商、路由或核心版本后，重新验证受影响的路径；不把本次结果写成对未来所有主机的保证。
