# DNS 泄漏排查与 ClashMi 覆写

适用于 HTTP 出口正确但 DNS 检测出现国内解析器、同一 YAML 在 Mac 与手机结果不同，以及用户要求兼顾隐私、速度和既有分流的情况。这里记录可复用操作，不保存个人设备状态或真实节点配置。

## 先确定查询路径和目标

- 分开核验 HTTP 出口、DNS 上游及其连接策略、UDP/STUN 出口。三者不能互相证明；解析器数量也不等于泄漏数量。
- DNS 检测页面出现国内 ISP 是排查线索。结合新随机测试域名、实际配置及日志，区分应用覆写、系统解析旁路、规则有意直连、旧配置/缓存和解析器归属地误判，不凭一张截图锁定根因。
- DoH/DoT 证明传输加密，不代表请求经由 VPS；海外解析器也不保证其连接未直连。DNS 服务商的递归出口不必与 VPS IP 相同，不能要求所有检测到的解析器地址等于节点地址。
- 区分“代理域名不经本地 ISP 解析”和“所有域名的 DNS 都必须经 VPS”。后者可能改变国内 CDN 选址和延迟。用户要求保留国内直连优化时，不静默删除 `nameserver-policy`；用户要求全域严格 DNS 时明确其性能取舍并实测。

## ClashMi 的两个入口及其作用范围

以下入口按 2026-10-21 核验的官方源码记录；不同版本/语言应先核对实际页面和运行时配置。只处理用户选中的独立配置，避免影响其他机场。

### 优先：只让指定配置保留其 DNS

1. 打开配置列表，找到用户正在使用的独立配置，在该条目的“更多”菜单选择“编辑配置”。这是配置设置页面，不是直接编辑原始 YAML 的“编辑”项。
2. 找到“核心覆写”，显式选择“内置-不覆写”，按右上角确认保存。不要只保留“当前选择”，因为它可能继续跟随全局覆写选择。
3. 这会改变该配置的 App 覆写方式，不仅针对 DNS。当前官方源码的不覆写模式不注入内置 DNS、NTP、Sniffer、TLS，但仍携带 TUN 等平台设置；不能解释为“关闭 VPN”或“所有 App 设置均停用”。原本依赖其他覆写的配置应先检查有效结果。
4. 确认配置中的 `dns.enable` 仍为 `true`，实际 VPN/TUN 与 DNS 接管仍正常，保持用户原有规则模式、策略组和规则；断开并重新连接 VPN 后再检测。

依据：[配置级选项](https://github.com/KaringX/clashmi/blob/35c1b88722932204aaf9b16532314cb25b55058f/lib/screens/profile_settings_edit_screen.dart#L224-L299)、[不覆写模式保留和省略的字段](https://github.com/KaringX/clashmi/blob/35c1b88722932204aaf9b16532314cb25b55058f/lib/app/modules/clash_setting_manager.dart#L384-L405)。

### 备选：保留其他内置覆写，只停用 DNS 覆写

入口为“核心设置”内的“DNS”页面，关闭页面顶部的“覆写”；关闭后其他 DNS 编辑项变灰是预期表现。不要关闭“启用”来代替“覆写”，也不要关闭 TUN 的“DNS 劫持”。

这是内置 DNS 设置，可能影响其他使用内置覆写的配置；改之前核对作用范围和用户授权。若当前使用“内置-不覆写”，DNS 设置组可能已经隐藏，无需为了看到这个开关再切回全局覆写。当前配置可能另有自定义覆写，也要检查它是否修改 DNS。

依据：[DNS 页面与顶部开关](https://github.com/KaringX/clashmi/blob/35c1b88722932204aaf9b16532314cb25b55058f/lib/screens/group_helper.dart#L2351-L2384)、[DNS 设置组的显示条件](https://github.com/KaringX/clashmi/blob/35c1b88722932204aaf9b16532314cb25b55058f/lib/screens/group_helper.dart#L1871-L1920)。

### 为什么必须看最终配置

ClashMi 的订阅配置、自定义覆写和 App 内置覆写有优先级；最后一层可能重新引入国内解析器或 `system`。本次核验的内置 DNS 默认列表包含这些来源，但这不证明用户的已安装版本或当前设置正在使用它们。

检查“运行时配置”或可用日志：代理域名实际选用经目标策略组的加密 DNS，未被覆盖成系统 DNS 或非预期 fallback；国内域名仍遵循用户要求的策略。单看导入文件或开关位置不能证明已经生效。

依据：[官方覆写顺序说明](https://github.com/KaringX/clashmi-docu/blob/main/guide/faq.md#clashmi覆写是如何工作的)、[默认 DNS 列表](https://github.com/KaringX/clashmi/blob/35c1b88722932204aaf9b16532314cb25b55058f/lib/app/modules/clash_setting_manager.dart#L178-L225)。

## 保留速度与分流的调整顺序

1. 首先纠正错误的 App 覆写，让已验证的 DNS 策略生效；保持 `rules` 数组、规则提供者、节点认证和带宽参数不变。文档整理不应顺手修改 YAML 或线上服务。
2. 国外/代理域名可使用目标版本支持的 DoH 策略标记，例如 `https://cloudflare-dns.com/dns-query#VPS-GROUP`；组名必须存在。国内 CDN 解析策略按用户现状保留，不把所有域名盲目统一到远端解析器。
3. 分别检查 `default-nameserver`、`proxy-server-nameserver` 与代理域名解析器的引导路径。普通 IP DNS 不是加密 DNS，这些引导查询也不会仅因主 `nameserver` 加了策略标记就自动经 VPS；严格全域 DNS 方案还需处理引导，避免依赖环和系统回退。
4. 保留有效缓存，分别量测冷解析与缓存命中，以及 Claude 等实际目标的页面/静态资源耗时。只在数据指向 DNS 时改解析器，不把所有慢请求都归因于 DNS，不为了防泄漏盲目切换 fake-ip/关闭 UDP。
5. Hysteria2 本身依赖 UDP，不能用全局禁止 UDP 作为通用修复。WebRTC/STUN 通过实际 VPN 隧道单独验证；TCP 系统代理不能证明 UDP 已被接管。

## 手机与桌面的验收

| 检查 | 通过证据 | 不能作为通过证据 |
| --- | --- | --- |
| 实际配置 | 选中的配置、运行时 DNS 与预期一致，VPN 已重连 | 原始 YAML 写对或开关已关闭 |
| HTTP | 新建请求显示预期节点出口 | DNS 检测中的国家标签 |
| DNS | 新随机域名的解析路径/权威记录符合预定策略；无非预期 ISP 或系统旁路 | 解析器数量少、只命中缓存、仅检查系统 DNS 列表 |
| UDP/WebRTC | 实际客户端路径的 STUN 映射符合预期 | 节点写了 `udp: true` 或 HTTP 出口正确 |
| 分流 | 原规则内容与顺序保持，代表性国内/国外目标的匹配符合预期 | 为通过检测切到全局代理 |
| 速度 | 相近条件下比较冷/热 DNS 和实际目标耗时，记录异常或超时 | 保证对所有设备/运营商永远零影响 |

重连后用新的测试会话/随机域名复测，避免旧页面结果；分别验证用户实际使用的 Wi-Fi 和蜂窝网络。对 Mac 只做必要热加载，不重置 TUN 或断开全部用户连接来替代检查。手机已由用户完成设置时，保留其现状；只有用户提供相应检测结果，才将该项标为用户确认通过，“设置完成”不等于独立实测。

如果仍有非预期 DNS，获取最小必要信息：App/内核版本、配置级“核心覆写”选择、DNS 页面状态，以及脱敏后的有效 DNS 片段或相关日志。不要求完整含认证配置，不自动改系统 DNS、其他订阅或路由器设置。
