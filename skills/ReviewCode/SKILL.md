# ReviewCode — 代码 Review 技能

对用户提供（或 Agent 生成）的代码进行规范审查，按语言代码块分别分析。当前仅定义 **Go** 规则；其他语言后续补充。

## 触发条件

当用户要求 review 代码、检查代码规范、或在代码提交 / PR 创建前需要自动审查时使用本技能。

---

## 使用方式

1. **先读目标仓库自己的 `AGENTS.md` / `CLAUDE.md` / `README.md`**。仓库自身的规则优先于本技能；本技能是默认基线，冲突时以仓库规则为准，并在结论里说明分歧。
2. 本技能中的 `jxpkg/logs`、`errcode`、`task` 等是 JX 系仓库的既有设施。换到别的仓库时，先确认该仓库的等价设施再套用规则，**不要照搬包名**。
3. 严重度：**Error**（必须修复）、**Warning**（建议修复）、**Info**（提示）。

4. **本技能只含通用规则。** JX 平台专有的契约规则（`POST /v1/<domain>.<Action>` 路由与注册方法即鉴权边界、反射三参数 handler、DTO 与响应信封、分页白名单、内部接口分离）在 jx-developer 的 `references/api-rules.md`；k3s 交付与部署策略（镜像 digest、迁移 Job、探针、grace 预算、securityContext、NetworkPolicy）在 `references/cicd.md`。审查 JX 仓库时两者一起套用，审查其他仓库时只用本技能。

## 一、日志（LOG）

### LOG-01 使用仓库既有的日志设施，不引入第二套 [Error]

- 业务代码禁止用 `fmt.Println` / `fmt.Printf` / 标准 `log` / `println` 输出运行日志。JX 系统一用 `jxpkg/logs`（zap 封装）。
- logger 由进程入口初始化一次（`logs.ReloadConfig(module, cfg)`），`module` 成为每行的 `mod` 字段；业务代码通过 `logs.Get(name)` 或 context 版本获取。
- **禁止**自建全局 logger，**禁止**把 `*zap.SugaredLogger` 塞进结构体字段或参数层层传递。
- `fmt.Fprintln(os.Stderr, err)` 这类写法只允许出现在进程入口（main）。既有欠债（如 `jxpkg/config` 里的 `fmt.Printf`）不要在新代码里模仿。

### LOG-02 日志方法统一，禁止自造方法与包装 [Error]

- 一律使用既有方法：`logs.InfoContext` / `logs.WarnContext` / `logs.ErrorContext` 及其 `…f` / `…w` 变体。
- **禁止新增日志方法，包括"只是包一层"的便利函数** —— 除非用户明确要求。判据不是"好不好用"，而是"是不是已经有等价能力"。
- 三个具体理由，评审时照此说明：
  1. 既有包装用 `AddCallerSkip(1)` 校正调用点，再包一层会让 `caller` 字段指向包装函数而不是真实出错位置；
  2. 字段与默认值会在层层包装中漂移，同一事件在不同服务里长得不一样，排障时无法统一检索；
  3. 仓库已有明文规则：`jxone/AGENTS.md`「禁止创建只有转发作用的包装函数」、`jxaccount/AGENTS.md`「Prefer direct concrete code over wrappers used once」、`jxpkg/AGENTS.md`「Prefer the smallest concrete API over speculative modes, wrappers or aliases」。

### LOG-03 日志格式规范 [Error]

- 结构化字段，不要拼进消息。字段名与既有约定一致（`reqid`、`module` 等由封装注入；业务字段用 snake_case）。
- 消息是**稳定模板**，用于聚合检索；变量一律走字段：
  ```go
  // 错误：数据拼进消息，无法按值检索
  logs.ErrorContextf(ctx, "dao insert failed, name=%s, err=%v", name, err)

  // 正确：稳定消息 + 结构化字段
  logs.ErrorContextw(ctx, "dao insert failed", "name", name, "err", err)
  ```
- **不要把整个实体或完整请求体 dump 进日志或错误串**。`logs.JSON(entity)` 这类写法在仓库里有既有用法，但实体可能携带敏感字段，新代码要克制；确需记录时先走脱敏（见 LOG-06）。

### LOG-04 链路可追踪：request id 必须贯穿 [Error]

一次请求/任务必须能从入口一路追到落库与回调，缺任何一环都算 Error。

- **入站**：从 `X-Request-Id` 读取，缺失则生成一个，写入 context（JX 系落 `reqid` 字段），此后该 context 上的所有日志自动携带。
- **出站**：调用其他服务时**必须把当前 request id 透传到 `X-Request-Id`**。当前 JX 仓库普遍缺失此透传，跨服务调用会各自生成互不相关的 id —— 新代码必须补上。
- **异步任务**：任务 payload 必须携带发起方的 request id 与业务主键（任务 id、实体 id），worker 处理时把它们作为日志字段写入。禁止只靠 worker 自己的 id，否则无法从任务回溯到原始请求。
- **响应**：把 request id 回传给调用方，方便用户报障时引用（当前 JX 只在 CORS 里声明了暴露该头，却没有实际设置，属既有缺口）。
- **反例**：在 `services/dev*` 层直接用 `logs.Errorf(...)` 而非 `logs.ErrorContextf(ctx, ...)`，会丢掉整个 reqid，日志无法归链。

### LOG-05 覆盖率以「链路可追踪」为准，同一错误只记一次 [Error]

**必须有的日志**：

- 请求/任务的入口与出口（含结果状态）
- 状态跃迁（任务入队、领取、成功、失败、重试、终止）
- 外部依赖调用与结果（LLM、对象存储、支付、第三方 API）
- 降级、重试、熔断、限流触发
- 非预期空值导致的默认分支（禁止静默降级）

**不该有的日志**：

- 同一个错误在 DAO、service、handler 层层重复打印。**同一错误只在处理它的那个边界记录一次**（`jxx/AGENTS.md`：相同错误通常只在合适边界记录一次，不在 DAO、service 和 handler 重复输出）。
- 高频路径上的 Info 刷屏。

> **与旧版的区别**：早期规则要求「每个 `return nil, fmt.Errorf(...)` 前都必须写日志」。该规则会制造大量重复日志，且会让仓库里最规范的服务全量违规。判据是**链路可追踪**，不是**每条 return 前都有日志**。

### LOG-06 隐私与秘密：只记长度与指纹，不记原值 [Error]

- **禁止**记录：密码、JWT / access token / refresh token、cookie、CSRF、登录或邀请票据、验证码、API Key、完整 DSN、mTLS 私钥、完整配置对象。
- 需要排查身份或内容时，**只记长度与指纹**：
  - 长度：`len=32`
  - 指纹：`sha256=ab12ef…`（截断到 8 位足够比对）
  - 掩码：`a***@domain.com`（邮箱类）、`eyJhb…(len=842)`（token 类）
- **复用既有机制，不要另造**：GORM 的 `ParamsFilter`（丢弃绑定参数，避免密码/令牌进 SQL 日志）、worker 的 `redactTaskPayload` / `payloadForLog`（按 key 名匹配 `authorization|password|secret|token|api_key` 替换为 `[REDACTED]`）、邮箱掩码 `maskEmail`、上游错误体 `io.LimitReader(resp.Body, 4096)` 截断。
- 对外错误只返回稳定错误码 + 安全描述，详细原因只进脱敏日志。

### LOG-07 日志等级语义 [Warning]

- **Error**：需要人介入的异常。JX 系在 Error 级自动附加 stacktrace，不要滥用。
- **Warn**：可预期的业务失败、降级、空值兜底、非预期但可恢复的分支。
- **Info**：关键业务流程节点（任务生命周期、重要状态变更）。
- **Debug**：仅本地排查使用，不进默认级别。

## 二、错误处理（ERR）

### ERR-01 所有 error 必须处理 [Error]

- 禁止用 `_` 忽略 error 返回值。

### ERR-02 用 `%w` 保留错误链 [Error]

- 包装用 `fmt.Errorf("...: %w", err)`，禁止用 `%v` 把错误降级成字符串。
- **重点检查** `fmt.Errorf("%w: %v", sentinelErr, err)` 这种混合写法：它保住了 `errors.Is` 对哨兵的判断，却把底层原因截断成不可解析的字符串。需要同时保留哨兵与原因时，用 `errors.Join`，或把原因作为结构化字段记进日志后再返回哨兵。

### ERR-03 用 `errors.Is` / `errors.As` 判断错误类型 [Error]

- 禁止字符串比较或 `err.Error() == "..."` 判断错误类型。

### ERR-04 业务错误不用 panic；库包不得 `Fatal` / `os.Exit` [Error]

- panic 只用于不可恢复的编程错误（如初始化期的不变量违反）。
- `logs.Fatal`、`os.Exit` 只能出现在进程入口；库包与 service 包出现即为 Error。

### ERR-05 对外只返回稳定错误码与安全描述 [Error]

- 错误码走仓库既有体系（JX 系 `jxpkg/apis/errcode`，新增前先查是否已有同语义错误码）。
- 面向外部的消息不得泄露内部路径、SQL、DSN、第三方原始报文。

### ERR-06 入口层必须检查下层返回的 error [Error]

- handler / api 层调用 service 后必须检查 Go error，不能只看自定义 `res.Code`。忽略即为 Error。

### ERR-07 不要把日志当成错误处理 [Error]

- 只记日志不返回、不上报、不中断，等于吞掉错误。日志是证据，不是处理。

## 三、方法与抽象（ABS）

### ABS-01 先复用、再抽象、最后才是新写 [Error]

动手前按顺序回答，答不上来就不许写新方法：

1. 这个能力在**本仓库**里是否已经存在？（grep 同语义函数名、看既有 `services/dev*`、`pkgs/`、`utils`）
2. 若存在但签名不合用，是**扩大既有方法**更合理，还是新写？（优先扩大）
3. 若确实要新写，它属于哪一层？放在该层是否违反依赖方向？
4. 是否只是"把几行挪个地方"？如果是，就不要动。

### ABS-02 禁止为单一业务场景造一次性方法 [Error]

- 不得因为"当前这个业务需要"就临时造一个只被调用一次、且只服务这一条路径的方法或抽象。
- 一次性逻辑应内联在调用点；只有当**第二个真实调用方出现**、或它天然属于既有架构中的某个角色时，才提升为方法。
- 判断口径：这个方法名里如果带着某个具体业务名词（某业务实体、某页面、某任务类型），而它做的事其实是通用的（分页、组装、校验、重试、拼接 URL），就是违规 —— 应按通用语义命名并放到既有架构的对应位置。

### ABS-03 禁止只有转发作用的包装 [Error]

- 形如 `func Foo(ctx) { return bar.Foo(ctx) }` 的转发函数一律不得新增（`jxone/AGENTS.md`）。
- 例外：需要固定参数、统一错误映射、或作为接口实现时，包装是合理的 —— 但这种包装必须携带真实逻辑，并在注释里写明它存在的理由。

### ABS-04 公共包升级门槛：至少两个真实消费者 [Error]

- 新增公共 API / 把代码提到共享包前，必须指出**至少两个真实调用方**；只有一个消费者时，代码留在它自己的包内。
- 有明确业务归属的代码不要因为"以后可能复用"提前放进公共包。
- 反过来也一样：同一个 helper 在仓库里出现三份（例如同一段 MySQL 1062 判重逻辑被复制到 5 个文件、3 个不同函数名下），就是该提取的信号。

### ABS-05 依赖方向不得倒置 [Error]

- 分层调用方向必须单向（JX 系：`cmd → app → internal/apis → internal/dto → services/svr* → services/dev* → models/*`）。
- 禁止 `pkgs/`（或任何共享底层包）导入 `apps/`；`models` 不得依赖 `services`；`services/dev*` 不得依赖 Gin / `internal/apis` / `internal/dto`。
- `services/dev*` 必须接收 `context.Context`，不得返回 HTTP response 或 status。

### ABS-06 重复逻辑用聚合或提取复用 [Error]

- 禁止在同一个函数里对同一资源因触发条件不同而写两段相似逻辑。用一个 `bool` 变量聚合所有触发条件，只调用一次通用方法：

  ```go
  // 错误：两段独立逻辑，各自调用同一个昂贵操作
  if needA { SplitPDFToImages(ctx, url) }
  if needB { SplitPDFToImages(ctx, url) }

  // 正确：聚合后调用一次
  needSplit := needA || needB
  if needSplit { SplitPDFToImages(ctx, url) }
  ```

### ABS-07 优先否定条件提前 return，禁止链式嵌套降级 [Error]

- 禁止 3 层及以上 `if { if { if { ... } } }` 用于链式降级（每层只在成功时继续、失败时静默跳过）。
- 正确做法：把链式操作封装为返回 `(result, error)` 的函数，每步失败直接 `return nil, fmt.Errorf(...)`，调用方一次 `if err != nil` 处理降级。
- 前置步骤失败即无法继续时，用否定条件提前返回，而不是用 `if ok { ... } else { ... }` 包裹主流程。

### ABS-08 新增或大改函数要做复杂度与性能评估 [Warning]

- 评估时间复杂度与空间复杂度（标明 n 的含义）、最好/最坏/平均情况、可能的瓶颈点（循环内 SQL、大内存分配、阻塞 I/O）、内存可优化点（预分配容量、指针 vs 值）。
- 仅评估**新增函数**或**改动较大的函数**；日志、注释类小改动无需评估。

## 四、数据访问与性能（PERF）

### PERF-01 禁止 N+1：循环内逐条 SQL [Error]

查询一旦进入循环就是 N+1，必须挡在评审阶段。

**检测方法**（逐条执行，不要只看 diff 的表面）：

1. 找到改动里每一个 `for` / `range`，检查循环体内是否有 DAO 调用、`db.` 调用、或任何会发出 SQL 的封装。
2. 检查是否存在「查列表 → 遍历 → 再查每条」的三段式；这是最常见的形态。
3. 检查 service 层是否对 `[]ID` 逐元素调用 `GetByID`、逐元素 `Update`、逐元素 `Insert`。
4. 检查循环体内是否有面向外部服务的调用（LLM、对象存储、第三方 API）——同样按 N+1 处理。
5. 检查是否有 `strings.Contains` 之类的内存匹配替代了本应下推到 SQL 的条件。

**优化路径**：批量查询进内存 → 构建 `id -> obj` 的 map → 在需要处 O(1) 取用；写入侧改用批量方法。确需逐条时必须在注释里写明原因（数据量上界、外部接口只支持单条等）。

### PERF-02 已有批量接口必须复用，不得在调用方循环 [Error]

- DAO 已提供 `GetByIDs` / `GetListByCond` / `CreateBatch` / `UpdateMapBatch` 这类批量方法时，**必须复用**，禁止在调用方循环调用单条版本。循环调用单条是 N+1 的主要来源，也让批量能力形同虚设。
- 需要新的批量能力时，按既有 DAO 命名补齐到 DAO 层，而不是在业务代码里凑循环。
- 批量写入要注意单条 SQL 的参数上限与事务大小；超过阈值时分批，批大小用仓库既有约定，不要就地发明新常量。
- 同一份查询结果被多处需要的，取一次放进 map 复用，不要在同一个函数里对同一资源重复查询（见 ABS-06）。

### PERF-03 核心接口必须给出复杂度结论 [Warning]

对核心读接口（列表、搜索、导出）与核心写接口（批量生成、批量结算）要求作者给出：

- **n 是什么**（如 `n = 本次查询返回的行数`、`n = 项目下的任务数`）
- **时间复杂度**与**最坏情况**（全表扫描？全量加载？无上限的分页？）
- **瓶颈点**与其优化方向

说不出 n 是什么，通常说明这段代码没有考虑过数据增长。

### PERF-04 分页、上限与索引 [Warning]

- 列表接口必须分页，且分页大小有上限；不接受「先全查出来再切片」。
- 模糊匹配下推到 SQL（`LIKE`）并配合索引，禁止拉全量到内存用 `strings.Contains` 过滤。
- 排序与过滤用到的字段要有索引；新增查询条件时确认索引是否存在。
- 深分页（大 offset）要有替代方案（游标/键集分页），或明确说明数据量上界。

### PERF-05 事务粒度与外部调用 [Warning]

- 事务内不得发起外部网络调用（LLM、第三方 API、对象存储），否则事务被网络抖动拖长，放大锁竞争。
- 长事务要拆：把外部调用移到事务外，用状态机/幂等键衔接。
- 事务边界要明确写清谁是权威存储、覆盖哪些写操作。

## 五、重试、超时、熔断与后端依赖（RES）

### RES-01 出站调用必须有超时 [Error]

- 禁止使用 `http.DefaultClient`、`&http.Client{}` 或不设超时的客户端 —— 它们没有超时，会把连接和 goroutine 一直挂住。仓库里已存在这类写法（`jxpkg/llm`、`jxone/pkg/llm`、`svrvoice` 的兜底分支、`new-api` 的 ollama 通道），新代码不得再增加。
- 数据库、Redis、对象存储、队列的调用同样必须有超时或可取消的 context。

### RES-02 超时按总预算分配，而不是只设单次尝试 [Error]

- 先确定**整条链路的总预算**，再决定每次尝试的超时与重试次数，保证 `尝试次数 × 单次超时 + 退避 ≤ 总预算`。
- 同一链路各段预算要量级匹配。参考现有约定：worker 长轮询约 51s → HTTP drain 60s → 进程退出 75s；整请求预算下不足最小剩余额度时不再发起新尝试。
- 重试不得把上游已经放弃的请求继续拖住。

### RES-03 重试必须幂等 [Error]

- 重试任何写操作前，先确认它可安全重放。可用的既有机制：
  - 幂等键（请求摘要绑定，摘要不一致返回冲突码）
  - 唯一索引 / 唯一约束（如对 `(ParentRunID, ParentRuntimeCallID)` 建唯一索引）
  - 预留-结算模式（先 reservation、再 settle，崩溃后可查预留恢复）
  - 任务重做预算（`redo <= max_redo` 的声明式重试，而不是在代码里循环重试）
- **不能重放的写操作不允许自动重试**，只记录并转人工/转补偿。

### RES-04 重试要有预算、退避与抖动，并区分可重试错误 [Warning]

- 重试必须有限次数、有退避、有抖动（避免同时重试打垮下游）。
- 必须区分可重试与不可重试错误：参数错误、鉴权失败、业务规则拒绝、上游明确返回"不可重试"的错误都不应重试。仓库里已有可参考的判定模型（`search-x` 的 `Retryable` 标记、`new-api` 的 `IsSkipRetryError`）。
- 重试要在日志里留下痕迹（第几次尝试、上次失败原因），否则排障时只看到成功那次。

### RES-05 熔断、隔离与限流：有则复用，无则至少 fail closed [Warning]

- 仓库里已有实现时必须复用，不要另造：`search-x` 的 provider 隔离/限流/信任度模型、`new-api` 的限流中间件。
- 没有实现时，至少要求：依赖不可用时 **fail closed**（`jxone/AGENTS.md`：依赖不可用必须 fail closed），有明确降级路径，并且降级要打警告日志（禁止静默降级）。
- 并发度要有上限：固定 routine 数的 worker 池、队列容量上限、并发上限；禁止无界 goroutine。

### RES-06 后端依赖分析：改动必须说明涉及哪些后端及其失败模式 [Error]

Review 时要求作者回答（答不上来即为 Error）：

1. 这次改动**涉及哪些外部后端**（MySQL / Redis / ES / 对象存储 / LLM provider / 第三方 API / 内部服务）？
2. 每个后端的**失败模式**是什么（超时、限流、部分失败、返回不完整数据、连接断开）？
3. 失败时**用户可见行为**是什么（报错、排队、降级、静默）？是否 fail closed？
4. **超时 / 重试 / 降级**分别怎么配？
5. 是否可能产生**重复副作用**（重复扣费、重复生成、重复发信）？靠什么保证幂等？

### RES-07 并发与幂等：禁止「先查后写」竞态 [Error]

- 禁止 check-then-write：不能先查询再根据结果决定写入，中间存在竞态。改用唯一约束 + 冲突处理、原子更新、或锁 + 事务。
- 回调、消费、定时任务必须幂等：重复投递不得产生重复副作用。
- 事务边界要说清楚：谁是权威存储、事务覆盖哪些写操作。
- 长事务与超时锁要留意：Redis 锁在超时或分区后**不能**证明独占所有权。

## 六、通用 Go 质量（GEN）

### GEN-01 类型与常量定义 [Error]

- 业务枚举必须定义别名类型（`type Status string`），禁止用裸 `string` / `int` 传播。
- 魔法值必须用 `const` / `iota` 定义并带业务含义注释；禁止 `status == "normal"`、`role == 2`。

### GEN-02 导出符号注释与命名 [Error]

- 导出函数、方法、变量、结构体、字段的注释必须以**自身名字开头**，符合 `go doc` 规范。
- 注释只写业务含义、数据来源与约定；禁止对话式用语与无关关键词。
- 导出符号命名**禁止以包名作前缀**（`openai.Client` 而非 `openai.OpenAIClient`）；内部函数同理。

### GEN-03 注释完整性与表达规范 [Error]

- 注释必须是完整自解释的陈述句。禁止：括号补充式（`状态（正常/异常）`）、片段残句（`仅Go层使用`）、未完结式（`用于...`）、无解释的实现术语。
- 非导出符号同样遵循完整表达规范（可省略签名开头）。

### GEN-04 禁止循环内逐条 SQL [Error]

- 禁止在 `for` 内对列表每一项单独 insert / update / delete / select（N+1）。
- 正确做法：批量查询进内存，构建 `id -> obj` 的 map 后在需要处填充。确需逐条时必须在注释里说明原因。

### GEN-05 空容器默认值 [Info]

- map / slice 声明时给默认空值（`m := map[K]V{}`、`s := make([]T, 0)`），避免为补零值写 else 分支。

### GEN-06 `Find` 零行判断 [Warning]

- GORM 用 `Find` 查询时，零行返回的是非 nil 指针指向零值结构体，调用方应以 `.ID != 0` 之类判断是否命中，而不是 `!= nil`。

### GEN-07 独立进程不得依赖需初始化的全局配置 [Error]

- 独立子服务（worker / consumer / 独立 CLI）禁止引用需要主服务初始化才能使用的全局配置变量，否则它无法独立运行，表现为启动 panic 或配置缺失。
- 正确做法：主服务构建任务 payload 时把所需配置值注入，子服务只从 payload 读取，保证解耦与可独立测试。
- 附带要求：消费 payload 时必须校验关键字段非空，为空时打明显警告日志，禁止静默降级。

### GEN-08 启动入口改动必须经用户确认 [Error]

- `main.go` / `init.go` 等启动入口的任何改动都要先向用户确认，禁止静默新增：数据库迁移、第三方服务初始化、全局配置加载、新的外部依赖 import。
- 初始化顺序保持稳定（配置 → 数据库 → 缓存 → 模型迁移 → 服务启动），不要插入隐式副作用。

### GEN-09 生成物禁止手改 [Error]

- 代码生成产物（swagger docs、protobuf、生成的 client 等）禁止手工编辑；修改源注解或 schema 后执行该仓库的生成命令。

### GEN-10 提交范围与分支安全 [Error]

- `vendor/` 的改动禁止提交（除非用户明确要求）。提交前用 `git status` 核对，只添加业务文件。
- 本地调试残留不得提交：硬编码的本地 IP/端口、被注释掉的调试代码、临时开启的调试开关。
- **严禁向长期分支直推**：`main` / `master` / `feature/*` / `release/*` 及其他长期维护分支。所有变更走「切开发分支 → 提交 → MR/PR → 合入」。
- 分支命名：`fix/<desc>`、`feat/<desc>`、`refactor/<desc>`。
- Review 前检查：当前分支是否属于禁止直推类型；开发分支从哪个基线切出（`git merge-base`）；是否已存在对应 MR/PR 及其状态（已合并的分支不应再有新提交）。
- 用户要求向禁止分支直推时必须拒绝并说明风险。

### GEN-11 编译与校验 [Error]

- 在包含 `go.mod` 的模块根目录执行命令。
- 用**目标仓库自己的**构建与生成命令（从它的 `Makefile` / `AGENTS.md` / `README.md` 读取），不要沿用其他仓库的目标名。
- 改动涉及多个可独立构建单元时，每个都要分别编译验证。
- 编译失败时不得靠换目录或改命令规避。

### GEN-12 依赖管理与 vendor [Error]

- **依赖全部 vendor**：改动 `go.mod` 后必须执行 `go mod vendor`，并把 `go.sum` 与 `vendor/` 一并提交。
- **禁止手改 `vendor/`**。依赖变更只通过模块工具完成，改完 review 生成的 diff。
- **不引入新的外部包**，除非已经明确讨论过。能用标准库或仓库既有依赖解决的不加新依赖。
- 不得提交指向个人 fork 的 `replace` 指令。

## 七、密钥与敏感数据（SEC）

日志侧的脱敏见 LOG-06，对外错误见 ERR-05，集群侧的挂载方式见 DEP-07。本节管**代码与数据流**里的密钥处理。

### SEC-01 仓库与代码里不得出现真实凭据 [Error]

- 禁止把密码、token、DSN、私钥、cookie、webhook 地址写进代码、配置、测试、注释或文档。
- 示例文件（`.env.example`、`conf/*.yaml`）只放占位符，且必须是**明显不可用**的值（`change-me`、`unreachable` 主机名），不要放看起来像真的样例。
- 真实值只走 gitignore 的 `secrets/`、`.env.local` 或集群 Secret。

### SEC-02 凭据只从配置注入，且缺失时 fail closed [Error]

- 禁止在代码里写「没配置就用这个」的默认凭据兜底 —— 这是最常见的泄漏与越权来源。
- 依赖凭据的能力在凭据缺失时必须**拒绝服务**并给出明确日志，而不是降级到匿名或默认账号。
- 启动时校验必需凭据的存在性与格式（长度、编码、能否解码），不要等第一次调用才失败。

### SEC-03 脱敏必须覆盖所有出口 [Warning]

出口不止日志一处。逐一确认：

- 日志与错误串（LOG-06）
- 对外 API 的响应体与错误描述（ERR-05）
- 发送给第三方的 webhook / 通知 / 埋点载荷
- 管理端与调试接口的展示
- 任务 payload 与队列消息（跨服务传递时同样敏感）

只做其中一处等于没做。仓库已有机制优先复用：GORM `ParamsFilter`、worker `redactTaskPayload` / `payloadForLog`、`maskEmail`、上游响应体 `io.LimitReader` 截断。

### SEC-04 需要留证时只记不可逆信息 [Error]

- 只记长度、哈希指纹（截断到 8 位）、掩码形式，禁止记录原值。
- 用于比对的（校验码、票据、一次性凭据）不得回显用户输入的原值；比较使用恒定时间实现，且按 `用途 + 目标 + 上下文` 绑定，避免"同码通用"。

### SEC-05 凭据的传递面要最小化 [Warning]

- 凭据只在真正需要它的进程/作用域内存在；不得为了"以后可能用"把密钥注入到无关工作负载或全局配置。
- 跨服务调用不要把用户凭据转发给不需要它的下游；能换成短期票据或作用域令牌的就换。
- 新增 Secret 时必须同时确认：谁创建、谁可读、轮换方式、泄漏时的处置路径。

## 八、数据安全（DATA）

### DATA-01 严禁硬删除 [Error]

- **任何环境（测试、生产）的任何数据都不得物理删除**，无论它是不是业务表。
- 代码里出现物理删除（`DELETE FROM`、`Unscoped()`、`HardDelete`、清理脚本直接删表/删行）一律报 Error。
- 需要「清除」语义时用软删除或状态标记；确需物理清除的（如合规要求）必须单独确认并记录。

### DATA-02 软删除字段统一为 `deleted_at` [Error]

- 软删除字段名统一 `deleted_at`；不得另造 `is_deleted` / `deleted` / `status=deleted` 等并行约定。
- 查询默认过滤已删除记录；需要包含已删除数据时必须显式写出并说明用途。
- 唯一索引与软删除的交互要检查：软删后重建同名记录是否会撞唯一约束。

### DATA-03 表结构变更必须确认并落脚本 [Error]

- 涉及业务表结构的 DDL/DML 变更，**必须与用户确认后**，按迭代版本放入该项目的 SQL 变更脚本目录。
- 禁止在代码里隐式迁移（启动时 AutoMigrate、init 里建表）；迁移只由显式命令或迁移作业触发。
- 迁移脚本与被迁移的服务版本必须对应；迁移失败要中止而不是继续跑新代码。

### DATA-04 变更脚本要可评估、可恢复 [Warning]

- 说明影响面：涉及行数、是否锁表、预计耗时、是否需要停写。
- 能写成可重放（幂等）的就写成幂等；不可逆的要在脚本注释与 PR 描述里写明。
- 大表变更要有 backfill 与双写/切换方案，而不是一条 ALTER 直接上。

## Review 输出格式

对每个代码块按以下格式输出：

```
### [语言] 文件: `path/to/file.go`

| 规则ID | 严重度 | 行号列表 | 当前代码片段 | 改进建议 |
|--------|--------|----------|--------------|----------|
| LOG-04 | Error  | 42, 87, 103 | `logs.Errorf("call upstream failed")` | 改用 `logs.ErrorContextf(ctx, ...)` 并透传 `X-Request-Id` |
| ABS-02 | Error  | 215, 248 | `splitPDFForOrderA(ctx, url)` | 业务限定名 + 通用实现，复用既有方法 |
```

**输出规则：**

1. **规则 ID 必须精确**，禁止用泛化 ID 代替具体条款。
2. **行号列表必须完整**：同一违规的所有行号列在同一行，禁止只写第一行。
3. **同文件同规则合并**为一条。
4. **当前代码片段**摘录最能代表违规的一行，用反引号包裹。
5. 只报告违反规则的项，不重复合规代码。
6. 最后给出修复摘要：

```
## 修复摘要

### Error（必须修复）
- [ ] `path/to/file.go` 行 42, 87, 103 — [LOG-04] 出站调用未透传 request id
- [ ] `path/to/file.go` 行 215, 248 — [RES-01] 使用无超时的 http.Client

### Warning（建议修复）
- [ ] `path/to/file.go` 行 310 — [RES-04] 重试无抖动，且未区分不可重试错误

### Info（提示）
- [ ] `path/to/file.go` 行 55 — [GEN-05] slice 未预分配容量
```

每条格式：`文件路径 行 <行号列表> — [规则ID] 简要描述`，方便直接定位并修复。
